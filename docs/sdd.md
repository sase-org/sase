# Spec-Driven Development (SDD)

SDD is sase's approach to planning and executing multi-step implementation work. Instead of ephemeral plans that vanish
when an agent session ends, SDD persists **specs** and **plans** as first-class artifacts that are linked to the bead
tracker and commit history.

## Overview

The SDD workflow is:

1. **Spec** — A concise description of the problem or feature, written by the user or generated by an agent.
2. **Plan** — A detailed implementation plan with numbered phases, generated by the agent and approved by the user.
3. **Execution** — Each phase is tracked as a bead, and commits reference the plan and phase for traceability.

## File Structure

SDD files live in `specs/` and `plans/` directories. When `sdd.version_controlled` is enabled, these are at the project
root (checked into version control). Otherwise, they live in `.sase/sdd/` inside the primary workspace (tracked in a
local git repo).

```
specs/
├── feature_name.md            # Spec: problem statement / requirements
plans/
├── feature_name.md            # Plan: numbered phases with implementation details
```

### Spec Files

Spec files are the expanded prompt that was used to generate the plan. XPrompt references are resolved and directives
are stripped, producing a self-contained record of the intent behind the plan.

### Plan Files

Plan files contain the agent's implementation plan with a `created` timestamp in YAML front matter. For larger efforts,
plan files carry a bead ID in their front matter linking them to an epic in the bead tracker. Each phase of the epic
gets its own bead whose ID appears in the corresponding commit messages.

For smaller plans, commit messages include a `PLAN=<path>` tag pointing back to the plan file.

## Configuration

SDD is configured in `sase.yml` under the `sdd:` section:

```yaml
sdd:
  version_controlled:
    false # true: specs/ and plans/ at project root
    # false: .sase/sdd/ in primary workspace (default)
```

When `version_controlled` is `false`, sase initializes `.sase/sdd/` as a standalone git repo with its own bead tracker,
auto-committing spec and plan files as they are created.

## Integration with Beads

SDD integrates with the [bead tracker](beads.md) for larger efforts:

- **Epics** — A plan can be promoted to an epic bead, with each phase becoming a child bead.
- **Phase tracking** — Each phase bead carries its own status lifecycle, allowing agents to claim and work on individual
  phases independently.
- **Commit linking** — Commit messages reference the phase bead ID, creating a traceable chain from epic to phase to
  commit.

See [`docs/beads.md`](beads.md) for the full bead system documentation.
