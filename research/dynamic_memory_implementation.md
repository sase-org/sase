# Dynamic Memory (`memory/dynamic.md`) Implementation Research

## Problem Statement

AGENTS.md defines a three-tier memory system:

- **Tier 1 (always loaded):** `@memory/build_and_run.md`, `@memory/glossary.md`, `@memory/gotchas.md`,
  `@memory/workspaces.md` — loaded via `@`-import on every session.
- **Tier 2 (dynamic):** `@memory/dynamic.md` — described as "dynamically generated by sase based on the user's prompt."
  **Not yet implemented.**
- **Tier 3 (long-term):** `external_repos.md`, `generated_skills.md` — listed with descriptions, agent reads on demand.

The design intent is clear: analyze the user's prompt before the agent session starts and write a `memory/dynamic.md`
file to the workspace so the agent receives only the context relevant to its task. Today, there is no code that does
this — the reference in AGENTS.md is aspirational.

## Architecture Context

Understanding the execution flow is critical for choosing where to hook in.

### How memory files reach the agent

```
User prompt → sase TUI/CLI
  → spawn_agent_subprocess() [launcher.py]
    → run_agent_runner.py (subprocess, cwd=workspace_dir)
      → prepare_workspace() — clean + checkout
      → extract_directives_and_write_meta()
      → run_execution_loop()
        → invoke_agent() [_invoke.py]
          → ClaudeCodeProvider.invoke() — spawns `claude` CLI
            → Claude Code reads CLAUDE.md from cwd
              → @AGENTS.md
                → @memory/dynamic.md (if it exists on disk)
```

Key constraint: `@memory/dynamic.md` is resolved by the agent runtime (Claude Code, Gemini CLI, etc.), not by sase's
preprocessing pipeline. The file must exist **on disk in the workspace directory** before the runtime reads AGENTS.md.

### Available hook points

| Location                                                                 | When                       | Has prompt?        | Has workspace?  | Notes                                                                              |
| ------------------------------------------------------------------------ | -------------------------- | ------------------ | --------------- | ---------------------------------------------------------------------------------- |
| `launcher.py:spawn_agent_subprocess()`                                   | Before subprocess spawn    | Yes                | Yes (path only) | Workspace not yet prepared                                                         |
| `run_agent_runner.py:main()` after `prepare_workspace()`                 | After workspace is clean   | Yes                | Yes (cwd)       | **Best hook point** — workspace is ready, prompt is available, before any LLM call |
| `run_agent_runner.py:main()` after `extract_directives_and_write_meta()` | After directive parsing    | Yes (cleaned)      | Yes             | Directives extracted, prompt has `#xprompt` refs expanded                          |
| Inside `run_execution_loop()`                                            | Just before LLM invocation | Yes (preprocessed) | Yes             | Too late — preprocessing has already happened                                      |

### Current tier 3 files (the selection pool)

| File                  | Lines | Content                                                                            | Relevant when...                              |
| --------------------- | ----- | ---------------------------------------------------------------------------------- | --------------------------------------------- |
| `external_repos.md`   | 25    | Chezmoi repo, plugin repos (sase-github, sase-google, sase-telegram, sase-nvim)    | Cross-repo work, chezmoi, plugins             |
| `generated_skills.md` | 35    | Skill file generation pipeline, CLI/skill contract sync, commit skills per runtime | Modifying skill source files, commit workflow |

With only 2 files totaling 60 lines, the current pool is small. The design should accommodate growth.

## Candidate Approaches

### Approach A: Rule-based keyword matching

Define a mapping from keywords/patterns to tier 3 files. Before agent launch, scan the prompt and include matching
files.

```python
# Conceptual implementation
DYNAMIC_MEMORY_RULES: list[tuple[re.Pattern, str]] = [
    (re.compile(r"chezmoi|plugin|sase-github|sase-google|sase-telegram|sase-nvim", re.I),
     "memory/external_repos.md"),
    (re.compile(r"skill|init-skills|SKILL\.md|commit.*workflow", re.I),
     "memory/generated_skills.md"),
]

def generate_dynamic_memory(prompt: str, workspace_dir: str) -> None:
    matched_files = []
    for pattern, memory_file in DYNAMIC_MEMORY_RULES:
        if pattern.search(prompt):
            matched_files.append(memory_file)
    if matched_files:
        content = assemble_dynamic_md(workspace_dir, matched_files)
        write_to(os.path.join(workspace_dir, "memory/dynamic.md"), content)
```

**Strengths:**

- Zero latency — no LLM call, no network request.
- Deterministic and debuggable — easy to test, easy to reason about.
- Zero cost — no tokens consumed.
- Cross-runtime compatible — writes a file to disk, works for any runtime.

**Weaknesses:**

- Brittle — novel phrasings ("update the chezmoi config" vs "modify dotfiles") may not match.
- Manual maintenance — every new tier 3 file requires adding rules.
- No semantic understanding — can't handle indirect references or implicit intent.
- Over-matching risk — broad patterns could inject irrelevant context.

### Approach B: LLM classifier (haiku/fast model)

Send the prompt + tier 3 file descriptions to a fast, cheap model. The model returns which files are relevant.

```python
CLASSIFIER_PROMPT = """
Given this user prompt and the available memory files, return a JSON list
of filenames that are relevant.

User prompt: {prompt}

Available files:
- external_repos.md: Chezmoi repo and plugin repo locations and workflows.
- generated_skills.md: Skill file generation pipeline, CLI/skill contract sync.

Return: ["filename1.md", ...] or [] if none are relevant.
"""
```

**Strengths:**

- Semantic understanding — handles paraphrasing, indirect references, implicit intent.
- Self-maintaining — adding a new tier 3 file only requires updating the description list.
- Can handle nuanced cases where keyword matching fails.

**Weaknesses:**

- Adds latency — even haiku adds 1-3 seconds to every agent launch.
- Adds cost — every agent session pays for a classification call.
- Non-deterministic — the same prompt could produce different selections.
- Overkill — for 2 files, a human can write exhaustive keyword lists in minutes.
- ETH Zurich finding — LLM-generated context _decreases_ performance by ~3%. While this was about generating content
  (not selecting it), it's a cautionary signal.

### Approach C: xprompt workflow integration

Create a built-in xprompt (e.g., `#dynamic_memory`) that's a workflow with a python step. The workflow analyzes the
prompt and generates the dynamic.md file as a side effect.

```yaml
# src/sase/xprompts/dynamic_memory.yml
name: dynamic_memory
steps:
  - name: generate
    type: python
    code: |
      from sase.memory.dynamic import generate_dynamic_memory
      generate_dynamic_memory(prompt, workspace_dir)
```

**Strengths:**

- Leverages existing xprompt infrastructure — no new execution mechanism needed.
- Composable — could be chained with other preprocessing xprompts.

**Weaknesses:**

- Fundamental architecture mismatch — xprompts process the **prompt text** sent to the agent, but dynamic.md needs to
  exist as a **file on disk** before the agent runtime reads AGENTS.md. The xprompt system doesn't write files to the
  workspace.
- Would require extending xprompt workflows with "write file" side effects, which is a larger change.
- Ordering complexity — must run before the agent runtime reads AGENTS.md but after workspace preparation.

### Approach D: Pre-launch hook in the runner

Add a dedicated `generate_dynamic_memory()` function called from `run_agent_runner.py` after workspace preparation. This
is a direct, minimal approach that doesn't try to fit into an existing subsystem.

```python
# In run_agent_runner.py, after prepare_workspace():
from sase.memory.dynamic import generate_dynamic_memory
generate_dynamic_memory(prompt, workspace_dir)
```

The `sase.memory.dynamic` module would own:

1. A registry of tier 3 files with their descriptions and relevance signals.
2. A selection strategy (starts as keyword matching, swappable to LLM later).
3. File assembly and writing logic.

```python
# src/sase/memory/dynamic.py
@dataclass
class MemoryEntry:
    path: str           # Relative to repo root, e.g. "memory/external_repos.md"
    description: str    # One-line description for LLM classifier (future)
    keywords: list[str] # Keyword patterns for rule-based matching

TIER3_REGISTRY: list[MemoryEntry] = [
    MemoryEntry(
        path="memory/external_repos.md",
        description="Chezmoi repo and plugin repo locations and workflows",
        keywords=["chezmoi", "plugin", "sase-github", "sase-google",
                  "sase-telegram", "sase-nvim", "dotfile"],
    ),
    MemoryEntry(
        path="memory/generated_skills.md",
        description="Skill file generation pipeline, CLI/skill contract sync",
        keywords=["skill", "init-skills", "SKILL.md", "commit workflow",
                  "commit skill"],
    ),
]

def generate_dynamic_memory(prompt: str, workspace_dir: str) -> None:
    """Analyze prompt and write memory/dynamic.md with relevant tier 3 content."""
    selected = select_relevant_entries(prompt, TIER3_REGISTRY)
    if not selected:
        # Remove stale dynamic.md if nothing is relevant
        dynamic_path = os.path.join(workspace_dir, "memory", "dynamic.md")
        if os.path.exists(dynamic_path):
            os.unlink(dynamic_path)
        return
    content = assemble_content(workspace_dir, selected)
    write_dynamic_md(workspace_dir, content)
```

**Strengths:**

- Minimal and direct — no new subsystems, no architecture changes.
- Clean separation of concerns — selection strategy is isolated and swappable.
- The registry structure supports future LLM classification (descriptions are already there).
- Easy to test — pure function with file I/O.
- Cross-runtime compatible — just writes a file.

**Weaknesses:**

- New module to maintain.
- The registry duplicates information already in AGENTS.md tier 3 descriptions (though the formats differ).

### Approach E: Derive from AGENTS.md tier 3 section (single source of truth)

Instead of a separate registry, parse the tier 3 section of AGENTS.md itself to discover available files and their
descriptions. Add keyword annotations as YAML frontmatter in each tier 3 file.

```markdown
## <!-- memory/external_repos.md -->

## keywords: [chezmoi, plugin, sase-github, sase-google, sase-telegram, sase-nvim, dotfile]

# External Repos

...
```

The generator reads AGENTS.md to find tier 3 entries, reads each file's frontmatter for keywords, and selects based on
prompt matching.

**Strengths:**

- Single source of truth — AGENTS.md is the canonical list, no registry to keep in sync.
- Adding a new tier 3 file only requires adding it to AGENTS.md and adding frontmatter.
- Frontmatter keywords are co-located with the content they describe.

**Weaknesses:**

- Parsing AGENTS.md markdown is fragile — format changes break the parser.
- Frontmatter in memory files adds noise that the agent also sees when reading the file.
- More moving parts than Approach D for little practical benefit at current scale.

## Comparison Matrix

| Criterion              | A: Keywords | B: LLM  | C: xprompt | D: Runner hook    | E: AGENTS.md parse |
| ---------------------- | ----------- | ------- | ---------- | ----------------- | ------------------ |
| Latency                | None        | 1-3s    | None       | None              | None               |
| Cost per launch        | $0          | ~$0.001 | $0         | $0                | $0                 |
| Semantic understanding | Low         | High    | Low        | Low (upgradeable) | Low (upgradeable)  |
| Maintenance burden     | Medium      | Low     | High       | Low-Medium        | Low                |
| Cross-runtime          | Yes         | Yes     | Partial    | Yes               | Yes                |
| Testability            | High        | Medium  | Medium     | High              | Medium             |

## Recommendation: Approach D (Pre-launch hook in runner)

**Use a dedicated `sase.memory.dynamic` module called from `run_agent_runner.py`, starting with keyword-based
selection.**

### Justification

1. **Right hook point.** The runner already has the prompt and a prepared workspace. Adding one function call between
   `prepare_workspace()` and `run_execution_loop()` is minimal and non-disruptive.

2. **Keyword matching is sufficient today.** With 2 tier 3 files, a handful of keywords per file covers the realistic
   prompt space. The ETH Zurich study warns against LLM-generated context, and Approach B's latency/cost overhead isn't
   justified at this scale.

3. **Clean upgrade path.** The `MemoryEntry` dataclass already includes a `description` field. When the tier 3 library
   grows to 5-10+ files (where keyword matching becomes fragile), swapping the selection strategy to an LLM classifier
   requires changing one function — `select_relevant_entries()` — without touching the runner integration or file
   assembly logic.

4. **Avoids architecture mismatch.** Approach C forces file-writing side effects into the xprompt system, which is
   designed for prompt transformation. Approach E couples the generator to AGENTS.md's markdown format. Approach D keeps
   the dynamic memory system self-contained.

5. **Cross-runtime compatible.** Like all memory tiers, it just writes a file. Any runtime that reads
   `@memory/dynamic.md` (or its equivalent) benefits.

### Proposed implementation plan

1. Create `src/sase/memory/__init__.py` and `src/sase/memory/dynamic.py`.
2. Define `MemoryEntry` dataclass and `TIER3_REGISTRY` with the current 2 entries.
3. Implement `select_relevant_entries(prompt, registry)` using case-insensitive keyword search.
4. Implement `assemble_content(workspace_dir, entries)` — reads selected files and concatenates with headers.
5. Implement `generate_dynamic_memory(prompt, workspace_dir)` — orchestrates selection + writing + cleanup.
6. Call `generate_dynamic_memory()` from `run_agent_runner.py` after `prepare_workspace()` and
   `os.chdir(workspace_dir)`.
7. Add cleanup: remove `memory/dynamic.md` from the workspace after the agent run completes (avoid stale files in the
   workspace clone).
8. Add tests for selection logic and file assembly.

### Open questions

- **Should dynamic.md be gitignored?** Since it's generated per-session in workspace clones, it should probably be in
  `.gitignore` to avoid accidental commits. However, since workspaces are ephemeral clones that get cleaned before each
  run (`prepare_workspace()`), this may be moot.
- **Should the registry live in code or config?** Code (as proposed) is simpler and type-checked. Config (`sase.yml` or
  a `memory/registry.yml`) would let users customize without code changes. Start with code, move to config if needed.
- **What about non-tier-3 dynamic content?** The system could also inject git log snippets, bead context, or plan file
  content based on the prompt. This is a natural extension of the `generate_dynamic_memory()` function — add more
  "content sources" beyond tier 3 files. But start with tier 3 selection only.
