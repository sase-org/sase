# SASE web client research

Date: 2026-04-30

## Question

How should SASE build a first web client after the Rust backend migration,
using the Phase 9 direction from `research/202604/rust_backend_migration.md`
and the current codebase/commit state?

This note reviews the Rust migration state, recent commits, backend/API
transport choices, frontend stacks, local security constraints, and a staged
implementation path. It ends with a recommendation.

## Executive summary

Build the first SASE web client as a **local-first browser app served by a
loopback `sase-server`**:

- Add `crates/sase_server/` in the sibling `../sase-core` Cargo workspace.
- Use **axum + tower-http + tokio** for the local HTTP server.
- Use **REST/JSON with OpenAPI generated by utoipa** as the first API contract.
- Generate TypeScript API types with **openapi-typescript**.
- Build the client as a **Vite + React + TypeScript SPA** using TanStack Query,
  TanStack Router, TanStack Virtual, and TanStack Table where useful.
- Bind only to `127.0.0.1`, choose an ephemeral port, and use a short-lived
  local session token with Origin checks.
- Keep side effects command-shaped and auditable. For actions still owned by
  Python host logic, call the existing `sase` CLI or expose a deliberately
  narrow Python-host adapter rather than duplicating plugin/workspace behavior
  in Rust.

Do **not** start with Next.js, hosted multi-tenant sync, native gRPC, or a
Tauri-only desktop shell. Those may become useful later, but they complicate
the first useful web client without solving the main SASE constraints:
filesystem access, local process control, plugin execution, and parity with
the existing TUI.

## Current SASE context

### Rust migration state

`research/202604/rust_backend_migration.md` now records Phases 0-8 as shipped.
The important current-state facts:

- Rust is the only implementation for the shipped core operations. There is no
  `SASE_CORE_BACKEND`, no `SASE_CORE_DUAL_RUN`, no dispatcher, and no Python
  fallback for ported surfaces.
- `sase` depends on `sase-core-rs>=0.1.0,<0.2.0`.
- The stable Python facade lives under `src/sase/core/`.
- The Rust implementation lives in the sibling `../sase-core` Cargo workspace.
- The shipped Rust-backed operations cover parsing, query parsing, agent
  artifact scanning, status line/planner helpers, and pure Git query parsers.
- Python still owns host logic: file-path APIs, query evaluation helpers,
  graph-index construction, side-effecting status transitions, subprocess
  invocation, process liveness, filesystem mutation, TUI rendering, and plugin
  entry points.

Phase 9 in the migration note specifically says to add a `sase-server` binary,
prefer server-side filesystem access, use the Rust core for shared logic, start
local-first on `127.0.0.1`, avoid hosted multi-tenant design, and keep mutation
endpoints command-shaped.

That is still the right high-level direction, but the Python-owned host logic
means the first server should not pretend to be a complete Rust rewrite of the
application. It should expose Rust-native read/query/scan surfaces directly and
bridge to existing Python/CLI behavior for side effects until those surfaces
are intentionally ported.

### Sibling Rust workspace

Current `../sase-core/Cargo.toml` has only:

- `crates/sase_core`
- `crates/sase_core_py`

Workspace dependencies are minimal: `serde`, `serde_json`, `thiserror`, and
`regex`. The pure crate already avoids a PyO3 dependency, which is exactly what
a server crate needs.

The `../sase-core/README.md` is stale in places: it still describes early
opt-in Rust phases and says Python remains the default. Treat
`docs/rust_backend.md` and `research/202604/rust_backend_migration.md` in this
repo as the fresher source of truth.

## Product shape

A useful first web client should be an operational workbench, not a marketing
site. The first screen should mirror the high-value TUI surfaces:

- ChangeSpecs list with query/search, grouping, status, parent/child context,
  and detail panel.
- Agents list with running/done/waiting state, tags, workflow context, latest
  logs, and notifications.
- Prompt/workflow launcher for common `sase run`, repeat, mentor, and workflow
  actions.
- Command palette for actions that already exist in Ace.
- Artifact/log viewer that can render rich web-native output better than the
  terminal.

Do not begin with hosted sync. A hosted service changes the hard problems:
secret storage, project data residency, git credential access, plugin
execution, local process control, and workspace mutation. The current SASE
model is local and filesystem-centric, so the first web client should be local
too.

## Backend/API options

### Option A: Rust axum server with REST/OpenAPI

Shape:

```text
../sase-core/
  crates/sase_core/       # existing pure core
  crates/sase_core_py/    # existing PyO3 extension
  crates/sase_server/     # new axum binary

sase web
  -> starts or locates sase-server
  -> opens http://127.0.0.1:<ephemeral>/
  -> browser SPA talks to same-origin /api/*
```

API examples:

```text
GET  /api/health
GET  /api/projects
GET  /api/changespecs?project=...&query=...&group_by=...
GET  /api/changespecs/{name}
GET  /api/agents?project=...&state=...
GET  /api/agents/{id}
GET  /api/events
POST /api/changespecs/{name}:transition
POST /api/agents/{id}:kill
POST /api/agents/{id}:tag
POST /api/workflows:launch
```

Pros:

- Aligns directly with Phase 9.
- Reuses `sase_core` without Python/PyO3 for read-heavy paths.
- Can serve static SPA assets and API from one same-origin loopback server.
- OpenAPI gives a stable contract for future web/mobile/desktop clients.
- axum fits SASE's modular needs: routing, extractors, JSON responses, tower
  middleware, tracing, compression, authorization, and later WebSocket/SSE
  support.

Cons:

- Rust core is not yet the whole SASE application.
- Mutating operations still need Python host logic, CLI subprocesses, or new
  host adapters.
- Binary packaging has to be solved: source dev is easy; PyPI/uv-tool release
  needs a plan.
- Cross-repo development gets more coupled: this Python repo and `../sase-core`
  must evolve together.

Assessment:

Best long-term backbone and best first implementation if scope is kept narrow:
read/query/scan/status first; command-shaped side effects bridged carefully.

### Option B: Python FastAPI/Starlette server

Shape:

```text
sase web
  -> starts an ASGI server in the Python package
  -> handlers call existing Python facades/actions directly
```

Pros:

- Fastest path to complete behavior because the existing product is Python.
- Direct access to plugins, workspace providers, subprocess helpers, locks,
  status transitions, and TUI-adjacent models.
- Built-in OpenAPI if using FastAPI/Pydantic.
- No Rust binary packaging problem beyond the already-required PyO3 wheel.

Cons:

- Cuts against Phase 9's server-in-Rust direction.
- Adds a new Python web stack and model layer.
- Risks freezing Python host dataclasses as public API unless a wire contract
  is enforced.
- Mobile/offline/shared-core story remains weaker.

Assessment:

Reasonable if the goal is a quick internal prototype with many existing
commands, but not the best architectural anchor. It is a fallback if Rust
server packaging or host-logic bridging becomes too slow.

### Option C: Rust axum server plus Python sidecar/CLI bridge

Shape:

```text
browser SPA
  -> axum local server
      -> direct sase_core calls for read/query/scan
      -> `sase` CLI subprocess or narrow local adapter for mutations
```

Pros:

- Keeps the Phase 9 server shape.
- Avoids rewriting Python-owned host behavior in Rust.
- Command subprocesses are naturally auditable and match existing CLI
  contracts.
- Can migrate command internals from CLI subprocess to native Rust or a
  structured Python adapter endpoint one command at a time.

Cons:

- Subprocesses add latency and error-normalization work.
- Needs discipline to avoid generic "run arbitrary shell" endpoints.
- Some commands may need richer progress streaming than a simple request/response
  endpoint.

Assessment:

Best practical MVP shape. It respects both truths: Rust is the shared core, and
Python still owns important host behavior.

### Option D: Native gRPC/tonic API

Pros:

- Strong schema-first contracts with `.proto`.
- Good fit for internal service-to-service or future non-browser clients.
- tonic is mature in Rust and built for high-performance gRPC over HTTP/2.

Cons:

- Browser clients do not speak native gRPC directly; gRPC-Web/Connect or a
  proxy layer is needed.
- Protobuf contracts are less convenient for ad hoc local debugging than
  JSON/HTTP.
- SASE's initial client needs simple local browser ergonomics more than
  polyglot microservice transport.

Assessment:

Do not start here. Reconsider if mobile/remote services become first-class or
if bidirectional streaming becomes central enough to justify protobuf tooling.

### Option E: rspc/Specta/ts-rs type-safe RPC

Pros:

- Strong Rust-to-TypeScript type sharing.
- rspc is transport-agnostic and can sit behind axum or Tauri.
- ts-rs and Specta can export Rust types to TypeScript with good developer
  experience.

Cons:

- Less standard than OpenAPI for external tooling, docs, debugging, and future
  non-TypeScript clients.
- More framework-specific coupling between server and client.
- SASE already has explicit wire records and a Phase 9 note calling for
  OpenAPI or `.proto` as source of truth.

Assessment:

Useful as a later developer-experience enhancer, but OpenAPI is the better
first public contract. If OpenAPI generation becomes painful for the Rust wire
types, `ts-rs` can generate internal UI-only types, but it should not replace
the API contract initially.

### Option F: WASM-only web client

Shape:

```text
browser loads WASM-compiled sase_core subset
browser reads user files directly or via File System Access API
```

Pros:

- Interesting for query syntax highlighting and pure parser previews.
- Could support local file import/export demos without a server.

Cons:

- A normal browser cannot scan `~/.sase/`, manage processes, launch agents,
  kill workflows, run plugins, or mutate workspaces.
- File System Access API coverage and permissions are not enough for SASE's
  filesystem/process model.
- Would create a misleading product direction.

Assessment:

Use WASM only for tiny optional client-side helpers, such as query syntax
highlighting or parse previews. Do not use it as the main architecture.

### Option G: Tauri desktop app

Pros:

- Tauri can package the same web UI as a desktop app.
- It supports any frontend framework and uses Rust for application logic.
- It gives a native launcher, tray/menu integration, and tighter local
  permissions than a random browser tab.

Cons:

- It is a packaging shell, not the core web architecture.
- It adds desktop release complexity before the browser MVP has proven itself.
- A Tauri-only API can diverge from the browser/server API if not disciplined.

Assessment:

Good later packaging layer. Keep the first client as a local browser SPA served
by `sase-server`; then wrap the same UI in Tauri if users want a desktop app.

## Frontend stack options

### Vite + React + TypeScript SPA

Pros:

- Simple static build served by axum.
- No extra Node server at runtime.
- Excellent fit for a local operational app.
- Works cleanly with OpenAPI-generated types and TanStack libraries.
- Easy future Tauri reuse.

Cons:

- No built-in SSR, but SASE does not need SEO or public page rendering.
- Needs deliberate app-shell/state architecture.

Assessment:

Best first choice.

### Next.js App Router

Pros:

- Strong full-stack framework with React Server Components, server functions,
  routing, and production deployment conventions.
- Useful for hosted multi-tenant products.

Cons:

- Adds a second server/runtime beside `sase-server`.
- Server components and server actions do not help when the real privileged
  backend is a local Rust/Python process.
- Hosted assumptions increase complexity around auth, deployment, and data
  residency before SASE has that product requirement.

Assessment:

Wrong first fit. Revisit only if SASE intentionally builds a hosted service.

### SvelteKit

Pros:

- Smaller UI surface and good app ergonomics.
- Vite-based.
- Good choice if the team prefers Svelte.

Cons:

- Current repo has no frontend stack and no evidence of Svelte preference.
- React has stronger ecosystem fit for TanStack Table/Virtual/Query and
  operational dashboards.

Assessment:

Viable but not preferred.

## UI architecture

Recommended client stack:

- **Vite** for build/dev server.
- **React + TypeScript** for UI.
- **TanStack Router** for type-safe routes and search params.
- **TanStack Query** for server state, polling, mutation invalidation, and
  optimistic UI where safe.
- **TanStack Virtual** for agent lists, ChangeSpec lists, log views, and other
  long scrolling surfaces.
- **TanStack Table** only where table semantics are useful; use custom list/detail
  layouts for Ace-like grouped trees.
- **Radix UI or Base UI primitives** for accessible dialogs, menus, popovers,
  tabs, and command palette internals.
- **CSS modules or plain CSS with design tokens** initially. Avoid adopting a
  large design system before the app's operational density is clear.

State split:

| State kind | Owner |
| --- | --- |
| Server snapshots: projects, ChangeSpecs, agent artifacts, notifications | TanStack Query |
| Live invalidation events | SSE first; WebSocket later if bidirectional UI events are needed |
| Route/search params: active project, query, selected entity, grouping mode | TanStack Router |
| Local UI: split sizes, open panels, modal state, command palette state | React/local store |
| Persisted SASE preferences: grouping mode, saved queries, tags | Server-backed settings endpoints |

The web UI should not copy Textual widget internals. It should reuse the same
domain contracts: wire records, grouping strategy names, command names,
duration choices, status transitions, and agent identifiers.

## API contract

Use REST/JSON for the first API:

- Human-debuggable with `curl`.
- Same-origin local browser app avoids most CORS work.
- OpenAPI gives generated TypeScript types and docs.
- Command endpoints are easy to name and audit.

Use utoipa in `sase_server` to generate OpenAPI from Rust request/response
types. Use openapi-typescript in the frontend build to generate `src/api/schema.d.ts`.

Do not expose generic filesystem write endpoints. Prefer commands:

```text
POST /api/changespecs/{name}:transition
POST /api/changespecs/{name}:archive
POST /api/agents/{id}:kill
POST /api/agents/{id}:dismiss
POST /api/agents/{id}:tag
POST /api/workflows:launch
POST /api/prompts:expand
```

Use structured errors everywhere:

```json
{
  "error": {
    "kind": "status_transition_denied",
    "message": "Cannot move Submitted ChangeSpec back to Ready",
    "detail": {},
    "correlation_id": "..."
  }
}
```

Recommended first endpoint slices:

1. `GET /api/health`: server version, `sase_core` version, workspace roots,
   current project detection, feature flags.
2. `GET /api/projects`: available `.gp` project files and archive state.
3. `GET /api/changespecs`: parse project/archive files through `sase_core`,
   apply query parsing, return list rows and grouping metadata.
4. `GET /api/changespecs/{name}`: full detail for selected item.
5. `GET /api/agents`: `scan_agent_artifacts` over `~/.sase/projects`.
6. `GET /api/agents/{id}`: detailed record plus resolved log/artifact paths.
7. `GET /api/events`: SSE stream for filesystem refresh hints and command
   progress.
8. A tiny mutation set: kill/dismiss/tag agent, transition ChangeSpec, launch
   one simple workflow.

## Live updates

Start with **server-sent events**:

- Browser support is simple.
- It fits one-way server-to-client refresh notifications.
- It keeps the mutation channel as normal HTTP POSTs.
- It avoids WebSocket protocol design for the MVP.

Event examples:

```text
event: changespecs_changed
data: {"project":"sase_102","reason":"project_file_mtime"}

event: agents_changed
data: {"project":"sase_102","reason":"artifact_scan"}

event: command_progress
data: {"command_id":"...","line":"..."}
```

Use polling as a fallback if SSE is flaky on a user's platform. Add WebSockets
only when the UI has real bidirectional needs such as interactive terminal
sessions or streamed agent/stdin control.

## Local security model

The web client is local, but local does not mean trustless security can be
ignored. A malicious webpage can try to talk to loopback services from the
user's browser.

Minimum controls:

- Bind to `127.0.0.1` only by default.
- Choose an ephemeral port.
- Serve UI and API from the same origin.
- Require an authorization token for every `/api/*` request.
- Use a one-time bootstrap URL that exchanges a nonce for a session token and
  then redirects to `/` without the nonce in the address bar.
- Check `Origin` and `Sec-Fetch-Site` on all state-changing requests.
- Disable permissive CORS. If CORS is needed for development, allow only the
  exact Vite dev origin and only in dev mode.
- Keep command endpoints narrow; never expose arbitrary shell execution.
- Log command invocations with user-visible command IDs.
- Do not allow remote bind addresses without an explicit flag and warning.

Remote access over SSH should use port forwarding:

```bash
ssh -L 8765:127.0.0.1:<server-port> host
```

Do not design LAN or hosted access in the first phase.

## Packaging and repo layout

Recommended layout:

```text
../sase-core/
  Cargo.toml
  crates/
    sase_core/
    sase_core_py/
    sase_server/
      Cargo.toml
      src/main.rs
      src/api/
      src/static.rs
      src/commands.rs

sase_102/
  web/
    package.json
    vite.config.ts
    src/
      api/
      app/
      features/
      routes/
      styles/
  src/sase/main/parser_web.py
  src/sase/main/web_handler.py
```

`sase web` in this repo should:

1. Resolve the `sase-server` binary.
2. Build/install it from `../sase-core` during source development when needed,
   following the pattern already used for `sase_core_rs`.
3. Start the server bound to `127.0.0.1:0`.
4. Pass necessary environment/config paths.
5. Open the browser unless `--no-open`.
6. Print the URL and server log path.

For released packages, there are three options:

| Packaging option | Notes |
| --- | --- |
| Python wheel includes prebuilt `sase-server` binaries | Best UX but requires release matrix work similar to `sase-core-rs`. |
| Separate `sase-server` release artifact downloaded/located by `sase web` | More moving parts and offline-hostile. |
| Source-only first | Acceptable for internal prototype, not for general users. |

Recommendation: source-only prototype first, then prebuilt binary release once
the web client is useful enough to ship.

## Testing strategy

Backend:

- Rust unit tests for API request/response serialization.
- Golden OpenAPI snapshot test.
- Handler tests with temp `.sase/projects` trees and synthetic artifacts.
- Command bridge tests that use fake `sase` executables or adapter traits.
- Health test that verifies the server sees the same core version expected by
  this repo.

Frontend:

- Typecheck generated API types.
- Component tests for core list/detail/control surfaces.
- Playwright e2e against a fixture server.
- Visual/screenshot checks for desktop and narrow mobile widths.
- Large-list performance tests with synthetic agents/ChangeSpecs.

Cross-repo:

- A `just web-check` target for JS lint/typecheck/tests.
- A `just server-check` target that runs `cargo fmt`, clippy, and tests for
  `crates/sase_server`.
- Update this repo's `just check` policy only after the prototype stabilizes;
  otherwise frontend tooling will slow unrelated Python changes.

## Risks

| Risk | Mitigation |
| --- | --- |
| Rust server reimplements Python host behavior incorrectly | Keep side effects behind CLI/adapter commands until a surface is deliberately ported. |
| API contract drifts from Python/Rust wire records | Generate OpenAPI from the Rust request/response types and add snapshot tests. |
| Localhost CSRF / drive-by web attacks | Token, Origin checks, same-origin API, no permissive CORS, command-shaped endpoints. |
| Cross-repo dev friction | Add explicit `just web-server-install`, `just web-dev`, and health checks; keep README/docs current. |
| Frontend overbuilds before product fit | Start with list/detail/command surfaces; avoid hosted auth, dashboards, and theming frameworks. |
| Agent/ChangeSpec lists get huge | Use server-side filters plus TanStack Virtual; do not render all rows as DOM nodes. |
| Event stream races produce stale UI | Treat SSE as invalidation hints; TanStack Query refetches canonical snapshots. |
| Packaging binary with Python release is non-trivial | Source prototype first; ship prebuilt server binary only after MVP validation. |

## Staged implementation

### Phase 9A: Read-only local web spine

- Add `crates/sase_server` with `GET /api/health`.
- Serve a minimal static Vite build.
- Add `sase web --no-open --port 0`.
- Implement token bootstrap and Origin checks.
- Add OpenAPI generation and TypeScript type generation.

Exit criterion: `sase web` opens a local app that shows server/core health.

### Phase 9B: ChangeSpecs and agents browser

- Add projects, ChangeSpecs list/detail, query parsing, and agent scan endpoints.
- Implement React list/detail UI with grouping and virtualized rows.
- Add SSE invalidation for project/artifact changes.

Exit criterion: the web UI can replace the TUI for passive inspection.

### Phase 9C: Narrow commands

- Add command IDs, command log/progress model, and SSE command progress.
- Add a small command set: kill/dismiss/tag agent; transition ChangeSpec;
  launch a simple workflow.
- Bridge to existing Python CLI or adapter traits for Python-owned behavior.

Exit criterion: the web UI can perform the most common safe operational actions.

### Phase 9D: Rich artifacts

- Add log/artifact browser.
- Render Markdown, diffs, images, and PDFs in web-native components.
- Reuse findings from `research/202604/tui_image_pdf_support.md` where relevant,
  but prefer normal browser rendering over terminal graphics protocols.

Exit criterion: web is materially better than the TUI for rich artifacts.

### Phase 9E: Packaging and optional desktop shell

- Decide prebuilt `sase-server` release packaging.
- Add Tauri wrapper only if users want an app shell.
- Revisit remote/hosted sync only with an explicit product requirement.

## Recommendation

Use **Option C: Rust axum local server + REST/OpenAPI + Vite React SPA, with a
Python/CLI bridge for host-owned commands**.

This is the best answer because it matches the migration's Phase 9 architecture
without overclaiming what the Rust core owns today. The shipped Rust surfaces
are exactly the high-volume read paths a web client needs first: parsing,
query parsing, agent artifact scanning, status planning, and pure Git parsers.
The side-effecting parts of SASE remain intentionally host-owned, plugin-aware,
and Python-centric. A command bridge lets the web client become useful now while
keeping those boundaries explicit.

REST/OpenAPI is preferable to gRPC for the first browser client because it is
debuggable, browser-native, and easy to type-generate. Vite React is preferable
to Next.js because the app is local, operational, and same-origin with a Rust
server; SSR and hosted full-stack conventions do not help the core problem.
Tauri is a good later shell around the same app, not the first architecture.

The first implementation should be deliberately boring: local loopback server,
ephemeral token, generated types, virtualized lists, query-backed snapshots,
SSE invalidation, and a small set of auditable command endpoints. That gets
SASE a real web client while preserving the core rule that made the Rust
migration successful: port behavior deliberately at stable seams, and do not
rewrite host logic just because a new UI exists.
